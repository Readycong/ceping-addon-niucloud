## 1. 项目概述

### 1.1 背景

中国心理健康服务市场处于政策与需求双驱动期，但付费意愿集中于 G 端（教育/政府）与 B 端（企业 EAP），C 端单独为"测评报告"付费的意愿很弱。因此本产品的定位**不是**做严肃心理评估工具，而是：

> **用趣味测评做流量入口，用广告变现兜住成本，用真实作答数据验证哪类需求最容易被转化。**

它是后期进入 G/B 端正经业务的**现金引擎与需求探针**，当前阶段不追求深度服务，只追求：**低成本上线、快速起量、跑通广告模型**。

### 1.2 产品目标

| 层级 | 目标 | 衡量方式 |
|---|---|---|
| 一期（MVP） | 50 个测评全量上线，跑通「答题 → 报告 → 广告 → 分享 → 复访」闭环 | 完成率 ≥ 70%、分享率 ≥ 8%【假设】 |
| 二期 | 广告收入覆盖 AI 与服务器成本 | 单日活月均 ARPU ≥ 成本【假设】 |
| 三期 | 沉淀需求地图，为 G/B 端业务提供已验证的需求与流量 | 各分类测评人次分布、分享率排序 |

### 1.3 北极星指标

**周活跃测评完成人次**（不是下载量、不是注册量——本产品无显式注册，且完成一次测评才产生一次广告曝光机会）。

### 1.4 本期不做（明确排除，防止需求蔓延）

- ❌ 显式注册/手机号绑定/微信昵称头像授权弹窗（仅静默获取 openid）
- ❌ 付费报告、会员订阅、虚拟货币
- ❌ 心理咨询师/机构对接与导流（合规风险高、供给端冷启动难，属后期 G/B 端业务）
- ❌ 抑郁/焦虑等临床筛查类测评【硬约束】
- ❌ 社交关系链功能、评论、UGC 内容（双人玩法仅展示匿名昵称与聚合结果，不做 IM）
- ❌ 题库在线编辑、运营数据看板（站点后台二期）
- ❌ web 电脑端测评页面（电脑端无测评场景）

## 2. 产品定位与边界

### 2.1 定位

**娱乐化趣味测评工具**。全部内容走"娱乐/性格/趣味"车道，与心理健康筛查严格切割。

### 2.2 内容红线【硬约束】

1. 全站不得出现抑郁、焦虑、双相、强迫症等临床概念，不得出现"筛查""诊断""风险""患病""就医""治疗"。
2. 是否展示非诊断声明**一律以题库 `compliance.nonDiagnostic` 字段为准**，该字段为 `true` 的测评，介绍页与结果页必须在显著位置展示声明，不可折叠。
3. 小程序类目必须选择**「娱乐 - 测试/占卜」**，**不得**选择「医疗健康」类目，否则触发资质审核。【硬约束】
4. 解锁机制只能用**激励视频广告**，**严禁**"分享给 N 人解锁""分享到 N 个群解锁"——微信重点打击的诱导分享行为。【硬约束】

### 2.3 版权策略（v2.0 调整）

1. **50 个测评全部上线**，无置灰项。5 个商业版权选题（#1/#3/#12/#37/#46）使用题库内**自编衍生题目**（`questions[]`），不上线 `originalItemBank` 中的还原样题。
2. 前台展示名清洗：题库 `title` 中「【商业版权·原题参考】」前缀**仅后台可见**，前台一律展示 `shortName` 或去前缀标题。
3. 风险提示：MBTI、九型、TKI、贝尔宾等名称与理论框架存在商标/版权主张可能；若收到权利人投诉，站点后台支持**一键下线单个测评**（无需发版）。

## 4. 用户与账号体系

### 4.1 静默 openid 登录（FR-01）

**需求描述**：用户首次进入小程序时，无任何授权弹窗，不索取昵称、头像、手机号，系统以 openid 静默建档。

**实现规则（niucloud 体系）**：

1. 前端 `wx.login()` 获取 `code`，调用框架现成接口 `POST /api/weapp/login`，请求体**只传 `code`**（不传 nickname/headimg/mobile）。
2. 站点会员配置固定为：**开启自动注册、关闭强制获取用户信息、关闭强制绑定手机号**（插件安装/配置检查项中给出提示）。
3. 框架 [WeappAuthService](file:///Users/chenqifang/aiProjects/aidiu-tools/niucloud/app/service/api/weapp/WeappAuthService.php) 以 `weapp_openid` 在 `member` 表查不到即自动建号，返回会员 token；前端存入 member store，后续请求自动带 token。
4. 插件**不新建 users 表**；测评业务表一律以 `site_id + member_id` 关联，需要 openid 时由 member 表读取。
5. 前台路由统一走 niucloud 中间件：`ApiChannel` + `ApiCheckToken(false)`（不强制登录，但带 token 即可解析出 member_id）+ `ApiLog`。答题提交、历史、AI、海报码等接口要求能解析到会员；未解析到时返回 401，前端重新走一次静默登录后重试。
6. H5 兼容端：微信浏览器走框架公众号授权链路；非微信浏览器降级为本地匿名 id（仅保证当次浏览与本地草稿，不承诺跨设备历史）。

**验收标准**：

- 新用户从进入到看见首页，全流程无授权弹窗、无登录页跳转；
- 同一用户换设备、清缓存后重新进入，昵称与历史记录**完全一致**（数据全部存服务端）。

### 4.2 站内昵称与头像（FR-02）

**需求描述**：昵称与头像**不是**微信资料，也不向微信索取任何用户信息。默认昵称由 openid **确定性推导**（无需存储）；用户可主动**修改昵称**（手动输入或一键随机重生成）、**从预设头像列表中挑选头像**。所有自设资料仅站内使用与存储。

**默认昵称算法**：

```
hash = sha256(openid + "salt_v1")        // 固定盐值
n1   = int(hash[0:8],  16) % ADJ.length  // 修饰词索引
n2   = int(hash[8:16], 16) % ANIMAL.length
nickname = ADJ[n1] + ANIMAL[n2]           // 例：深海鲸鱼、夜行的猫
```

- `ADJ`（16 个）：深海、夜行、慢半拍、发光、暴走、佛系、彩虹、沉默、奔跑、贪吃、清醒、毛茸茸、远山、雨天、碳酸、铁皮
- `ANIMAL`（16 个）：鲸鱼、猫、鹿、熊、狐狸、企鹅、水獭、兔子、刺猬、海豚、麻雀、乌龟、狼、羊、萤火虫、章鱼
- 默认头像：`sha256(openid + "salt_av") % AVATARS.length` 从预设头像列表确定性取一个

**实现规则**：

1. 服务端提供 `GET /api/ceping/profile`：返回当前会员生效中的昵称与头像（有自设用自设，否则返回确定性默认值，前端无法区分来源）+ 累计完成人次；**不写入 member 表，不取微信昵称头像**；
2. 服务端提供 `POST /api/ceping/profile`：保存自设昵称（1–12 字，去首尾空格，敏感词走通用过滤）与头像（avatar_key 必须命中预设列表，禁止上传）；
3. 自设资料存 `ceping_member_profile`（§9.2），删除自设资料即回退确定性默认值；
4. 首页/历史顶部用户信息区、AI 报告 `{{USER_NICKNAME}}` 变量、双人邀请页展示名均使用生效昵称；
5. 头像为**预设 emoji/插画列表**（24 个），点击头像弹出九宫格选择，点选即保存；点击昵称弹出编辑框（输入或「随机一个」重生成）。

**验收标准**：未自设时同一 openid 连续调用 100 次返回昵称完全一致；自设昵称/头像后换设备、清缓存仍生效；输入超长/纯空格被拒绝；头像只能从预设列表选择。

### 4.3 数据留存策略（FR-03）

- 所有测评记录、AI 报告、解锁记录、双人邀请关系**全部服务端持久化**（MySQL），不依赖本地缓存。
- 小程序本地存储仅用于：答题过程草稿（防中途退出丢答案，24h 有效）、题库索引/题库 JSON 版本缓存、AI 报告只读缓存。
- **历史记录不限保留数量**，同一测评可重复测，每次独立成行（见 §6.7）。

**验收标准**：卸载重装小程序后，历史列表完整恢复；删除历史后对应数据不可再被任何前台接口读出。

### 6.2 分类 Tab 与分类列表页（FR-11）

- 展示该分类下全部**已上线**测评卡片（MVP 为全部 50 个）；

### 6.3 测评介绍页（FR-12）

|---|---|

### 6.4 测评答题页（FR-13）

| 项 | 需求 |
|---|---|
| 题型 | 全部单选题，每题恰好 4 个选项（A/B/C/D） |
| 进度 | 主题化进度指示 +「第 n / N 题」，支持返回上一题修改 |
| 交互变体 | 由主题包声明：逐题翻转（默认）、左右滑卡、一屏多题滚动、对偶二选一（dimension） |
| 选中 | 点击选项即选中，默认延迟 250ms 自动进入下一题（防误触）；主题包可改为手动翻页 |

### 6.5 结果报告页（FR-14）

**双层报告结构**（核心设计）：

| 层 | 内容 | 来源 | 时延 |
|---|---|---|---|
| 第一层：静态报告 | 结果名、一句话摘要、80–200 字解说、特质标签、成长建议 | 题库 `results[].detail` | 0ms，立即渲染 |
| 第二层：AI 深度报告 | 4 段结构化解读 + 作答回扣 `answerEcho` | 大模型生成（见 §10） | 看广告解锁后异步 2–8s |

**图表变体（随主题包/计分模型）**：

- `category`：各分类得分**横向条形分布**，高亮第一名并标注第二名分差；
- `threshold`：**档位仪表盘/进度条**，标注总分与所处区间位置；
- `dimension`：**多维轴图/象限标签**（如 EI/SN/TF/JP 四轴取向）；
- 双人契合度：**双环契合分 + 同频/分歧题分布**（见 §6.8）。

**解锁策略（固定方案 A）**：静态报告免费全显；AI 深度报告需**观看激励视频**后由服务端校验并触发生成（见 §7.3、§10.6）。无任何分享解锁入口【硬约束】。

**验收标准**：

- 静态报告提交后 ≤ 300ms 渲染；
- AI 报告无论成功/失败/超时，页面永不空白（降级静态内容 + 友好提示）；
- 已解锁报告二次查看（历史详情）不重复扣广告、不重复调用模型。

### 6.8 #7 契合度：单人版 + 双人版（FR-17）

题库 `007_relationship_compatibility.json` 为 10 题 threshold（每题 0–3 分，满分 30，4 档：各玩各的 0–7 / 需要磨合 8–15 / 默契上线 16–23 / 天生一对 24–30）。

**6.8.1 单人版**

- 用户以「我如何看待当下这段关系」的视角独立作答 10 题；
- 按现有 threshold 规则计分落档；静态报告、AI 报告、海报与其他测评完全一致；
- 介绍页文案与答题引导语使用单人视角措辞。

**6.8.2 双人版**

玩法链路：

```
A 在介绍页选「邀请 TA 双人测」
  → A 作答 10 题 → 提交（record 模式=partner_inviter，status=waiting_partner）
  → 服务端生成邀请（token，72h 有效）与邀请小程序码（scene=cp7-{token}）
  → A 分享给 B（转发卡片/邀请海报）
B 扫码 → 邀请承接页（展示 A 的生效昵称、玩法说明，不展示 A 的答案）
  → B 登录并作答同一套 10 题 → 提交（record 模式=partner_invitee）
  → 服务端配对计算，双方 record.status=paired、互写 partner_record_id
  → B 当场看到双人契合结果；A 在等待页 onShow/下次进入（历史/分享回流）看到结果
```

**双人契合度计分规则**（服务端 `partner` 计分器）：

1. 双方每题得分 `a_i / b_i ∈ {0,1,2,3}`，各自总分 `Sa / Sb`；
2. **同频度**（感知一致性）：`sync = Σ max(0, 3 − |a_i − b_i|)`，满分 30；同频题数 = `|a_i − b_i| = 0` 的题数；
3. **关系温度**（双方感知质量均值）：`warmth = (Sa + Sb) / 2`；
4. **契合总分**：`pairScore = round(sync/30×60 + warmth/30×40)`（0–100，同频权重 60%、温度权重 40%）；
5. **结果档位**：以 `warmth` 落入题库现有 4 档 bands，复用现有 `results[]` 文案；结果页额外展示 pairScore、同频题数、**分歧最大的 2 道题的题面**（只提示"你们在这两题看法差异最大"，不暴露对方具体选项）；
6. 平票/边界沿用题库 `tieBreak`。

**双人 AI 报告**：在 007 提示词基础上由服务端追加双人上下文（双方各自答案轨迹、Sa/Sb、sync、分歧题面），输出 Schema 不变；`answerEcho` 围绕双方分歧与同频点撰写，**严禁披露对方具体选项、严禁评判对错**。生成时机与解锁方式同普通测评（见 §10）。

**边界规则**：

- 邀请 72h 未应答：状态 expired，A 可重新发起；A 可主动取消；
- B 不能应答自己发起的邀请（同 member_id 校验）；同一邀请仅可应答一次；
- A 在等待期可先看本人单人视角的静态摘要（不展示双人结论）；
- 双人结果对双方可见范围一致：聚合结果 + 分歧题面，不含逐题答案明细。

### 6.10 测评主视觉图规范（FR-19，v2.2 新增）

**需求描述**：为 50 个测评各配置一张高质感**写实摄影风**主视觉图（hero image），替代纯渐变色封面，提升高端感与信息流点击率。整体质感要求：真实摄影、无 AI 感（禁止过度光滑的塑料质感、不自然配色与插画风）。

**使用位置（同一张图三处复用，16:9 横图）**：

| 位置 | 呈现方式 | 可读性保障 |
|---|---|---|
| 首页信息流封面（信息流卡片头图） | `object-fit: cover` 铺满，`loading="lazy"` 懒加载 | 上/下双向渐变压暗层；`NO.xxx` 编号白字 + 主题 emoji 白底小角标 |
| 热门测评横滑卡 | 同上 | 下部深度压暗（约 75% 不透明度黑），`TOP n` 与标题白字 |
| 介绍页头区（Hero 区） | 铺满头区，**不懒加载** | 自上而下渐变至主题包卡底色 `var(--card)`，明暗两套主题下标题/标签均可读 |

**生成规范**：

1. Prompt 公式：`{该测评的具象生活场景（英文摄影语言）} + 固定后缀`；后缀统一为 `realistic photography, 35mm film, natural light, candid, editorial style, muted tones, no text, no watermark`；
2. 场景选取原则：与测评主题强关联的**具象隐喻**（如 #7 契合度=窗台两杯咖啡与雨城、#8 心态段位=山脊日出登山者剪影、#12 九型人格=九把古铜钥匙）；静物与人物剪影优先，避免可识别人脸特写与图中可读文字；完整 50 条映射见原型 `COVERS` 表与《[设计规范.md](设计规范.md)》附录；
3. 尺寸：16:9（`landscape_16_9`），成图横向 ≥ 1368px；
4. 风格红线：禁止插画/卡通/3D 渲染/霓虹赛博风/过饱和配色；图中禁止出现任何文字与水印；
5. 资产归属：开发期通过文生图 API 按 `COVERS` 映射批量生成，**正式上线前必须转存自有存储/OSS 并配置 CDN**，线上不依赖第三方生成接口；后台支持按 test_id 替换图片。

**实现规则**：

1. 图片以 `<img>` 绝对定位覆盖在主题渐变底之上，渐变底保留为**失败回退层**：`img onerror` 隐藏图片即露出渐变底，文字仍可读；
2. 层级固定：图片 z-index:0 → 压暗层 z-index:1 → 文字/角标 z-index:2；
3. 信息流与热门卡共 58 张图全部 `loading="lazy"`，介绍页头区首图不懒加载；
4. 海报 Canvas 绘制**不引用**远程主视觉图（避免跨域污染 `toDataURL`），海报内使用主题色版式。

**验收标准**：

- 50 张图全部可加载（原型已验证 59 处引用 0 失败）；
- 任一处加载失败自动回退主题渐变底，标题与编号文字仍满足对比度要求（≥ 4.5:1）；
- 图片层不遮挡任何点击热区；三处展示的裁切在主流机型上不出现主体被切关键部位。

## 7. 核心流程

### 7.1 首次进入

```
小程序启动 → wx.login() → POST /api/weapp/login {code}（框架静默建号，返回 token）
         → GET /api/ceping/profile（返回生效昵称/头像、累计完成数）
         → 渲染首页（金刚区/热门/列表）
```

### 7.2 答题与报告（AI 在解锁后生成）

```
P3 开始测试
  → P4 逐题作答（本地草稿）
  → 提交 POST /api/ceping/record/submit
       ├─ 服务端校验 + 独立复核计分（防篡改）
       ├─ 写 ceping_record
       └─ 返回 {recordId, resultKey, resultName, 静态报告, scoreDetail}
  → P5 立即渲染静态报告与图表（0ms 等待 AI）
  → 用户点「看视频解锁完整 AI 解读」
       ├─ 激励视频播放完成 → POST /api/ceping/ad/verify
       ├─ 服务端校验并写解锁记录（幂等）
       ├─ 命中本人历史同答案缓存 → 直接 ready（复制缓存内容为本 record 独立成报告）
       └─ 未命中 → 投递队列任务调 LLM
  → 前端轮询 GET /api/ceping/report/{recordId}（1s/2s/4s…，上限约 15s 后提示稍后再来）
```

> 与 v1.0 的差异：**AI 生成从「提交即生成」改为「解锁后才生成」**。只有完成激励视频的用户产生模型调用，AI 成本与广告收入严格对冲。

### 7.3 广告解锁

```
点「看视频解锁」→ uni.createRewardedVideoAd
  → 播放完成回调 → POST /api/ceping/ad/verify {recordId, adType}
       ├─ 校验：record 属于本人、广告类型合法、未解锁过
       ├─ 写 ceping_unlock_log → 返回 unlocked=true 并触发/复用 AI 报告
  → 广告未完成/加载失败 → 保持遮罩，允许重试，不产生解锁记录
```

## 8. 计分引擎规范

### 8.1 category（分类累加）

```
sum = {}  // 各分类累计得分
for (q, chosenOption) of answers:
    sum[option.score.cat] += option.score.points ?? 1
result = argmax(sum)
平票处理：按 results 数组顺序取靠前者（题库 tieBreak 字段为准）
```

### 8.2 threshold（分数区间）

```
total = Σ option.score.points
result = bands.find(b => b.min <= total && total <= b.max)
边界：分数落在档位边界时取高一级（题库 tieBreak）
```

### 8.3 dimension（多维轴组合）

```
for each axis:
    count[pole] += 1
    pole = 计数较高的一方（平票取 poles[1]）
match = {axisKey: pole, ...}
result = results.find(r => 所有轴 match 相等，"*" 为通配)
```

### 8.4 服务端复核【硬约束】

客户端计分仅用于即时渲染，**服务端必须用同一套 PHP 实现独立复核**，以 `ceping_record.result_key` 为准；校验项：题号连续完整、选项 key 存在、score 与题库一致。客户端篡改结果不影响落库结果与海报内容。

### 8.5 partner（#7 双人，服务端专用）

见 §6.8.2 公式；双人报告档位以双方均分 `warmth` 命中 bands，pairScore 单独存储于 `score_detail`。

## 10. AI 报告接入方案

### 10.1 LLM 客户端（插件自建）

- 框架无内置大模型能力，插件内自建 **OpenAI 兼容 HTTP 客户端**（Guzzle，chat/completions，支持 `response_format=json_object`）；
- 默认对接 DeepSeek，后台可改 base_url/key/model 以兼容通义、Kimi、OpenAI 等兼容服务；
- 配置存 `sys_config`（`CoreConfigService::getConfig/setConfig`），不入库到代码。

### 10.2 提示词加载

- 50 份提示词与 `prompts.json` 随插件资源发布；代码库只维护一份公共段 `_COMMON.md`（第五~七节），运行时拼接 `专属段(一~四) + 公共段(五~七)`，避免 50 份规则漂移；
- 服务端按 test_id 取 systemPrompt，替换全部 `{{VAR}}` 后作为 system 消息；替换后仍有 `{{...}}` 残留视为异常，不发送。

### 10.3 变量拼装（服务端职责）

| 变量 | 拼装规则 |
|---|---|
| `ANSWER_TRACE` | 逐行 `[题号] 题干 → 所选选项文本`；双人版附 B 的轨迹与分歧题 |
| `SCORE_DETAIL` | 按三种模型分别拼装（见 `提示词/README.md`）：category 带第二名与分差；threshold 带区间位置；dimension 逐轴取向 |
| `BASE_DETAIL` / `TRAITS` / `RESULT_NAME` / `RESULT_KEY` | 取题库命中结果 `results[]` |
| `USER_NICKNAME` / `DATE` | 生效昵称（自设优先，否则确定性默认）、测评完成日期 |

### 10.4 输出 Schema

```json
{
  "headline": "一句话定调，≤20字",
  "subline": "副标题，≤30字",
  "sections": [
    {"title": "01 核心解读", "content": "100-160字"},
    {"title": "02 你的具体表现", "content": "100-160字"},
    {"title": "03 优势，以及可能的代价", "content": "80-140字"},
    {"title": "04 一条能马上用的建议", "content": "60-120字"}
  ],
  "traits": ["特质1", "特质2", "特质3"],
  "answerEcho": ["你在「…」这题选了「…」，这透露出…"],
  "shareLine": "≤30字，结尾「你呢？」",
  "disclaimer": "本测试为娱乐性质，结果不代表专业心理评估或医学诊断。"
}
```

### 10.5 服务端必做的四道防线

1. **JSON 校验**：解析失败 → 重试 1 次（temperature 降至 0.3）→ 仍失败标记 `failed`；
2. **字段校验**：缺失/超长字段用静态报告对应内容补齐；
3. **禁词扫描**：对输出跑禁用表述清单（抑郁症/确诊/建议就医/高风险…），命中即 `failed`；
4. **降级**：任何失败情况下前端渲染静态 `detail`，AI 区展示「AI 解读生成中，稍后再来看看」或隐藏模块。**结果页永不空白。**

### 10.6 触发时机、队列与幂等

1. 仅在**激励视频解锁校验通过后**触发（§7.2）；
2. `ad/verify` 幂等：同一 record 重复回调只产生一条解锁记录；
3. 异步队列：`AiReportGenerate` Job 经 `BaseJob::dispatch()` 投递（生产用 Redis 队列，事务提交后投递）；前端轮询 `report/{recordId}`；
4. 状态机：pending → ready / failed；failed 允许用户再次触发（不重复扣广告）。

### 10.7 缓存与成本（每次作答独立留存，但不重复调模型）

- **缓存键：`member_id + test_id + answersHash`**（同会员、同测评、同组答案）；
- 命中缓存时：**不调用模型**，将历史报告 content **复制为本次 record 的独立 ai_report 行**（`is_cached=1`）。因此每次测评在用户历史里都有独立 AI 报告快照，可随该记录单独删除，而模型成本不重复发生；
- **不做跨会员共享缓存**：`answerEcho` 回扣本人作答，跨用户共享会泄露/串改他人答案；
- 单次估算：输入 2,300–2,600 token、输出 500–700 token【假设，待实测】；
- AI 总开关关闭或配置缺失：前端不展示解锁入口，产品退化为纯静态测评，链路完整可用。
